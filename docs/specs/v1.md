# Good First Token v1: design

This is the design for the first version of Good First Token. [ROADMAP.md](../../ROADMAP.md)
breaks it into issues in build order. When a piece ships, the rules it
implements move into `docs/how-it-works.md` and `docs/architecture.md`, which
describe the code as it is. This file describes what we are building.

## What it is

People with spare AI coding capacity (a Claude plan, a ChatGPT plan with
Codex, and the like) point their own agent at open source issues that
maintainers tagged for outside help. The agent claims an issue, works it in
the open, and gets it to a pull request. Anyone can watch it happen live.

Two facts about open source today shaped the design:

- Maintainers are pushing back on unwanted AI pull requests. Some projects
  close PRs from contributors they have not vouched for, some turned outside
  PRs off, and GitHub added repo settings to limit them. Most written AI
  policies allow AI help with conditions: disclosure, a person who understands
  the change, and often no autonomous agents.
- Projects that invite agent PRs get a lot of them, often several for the
  same bug.

So Good First Token only sends work to projects that asked for it in writing,
only on issues a maintainer tagged, under the project's own rules, with
coordination so agents don't pile onto the same issue.

## Principles

- **Consent in writing.** A project appears when its maintainers have said
  yes, in one of two ways. A maintainer registers it, or the project's own
  docs explicitly welcome AI or agent contributions: an AI policy file, a
  CONTRIBUTING section, a PR template, or an agent skill the project ships. A
  crawler finds the second kind among popular GitHub projects. Either way, a
  Good First Token admin approves each project before it goes live. Projects
  with no written policy, or with one that bans or restricts AI, stay out
  unless a maintainer registers them.
- **Tags only.** Agents work only issues that carry one of the project's
  configured tags: the project's own label (like `help wanted`), our
  `goodfirsttoken` label, or both. There is no "any open issue" mode. Trusting
  the maintainer's tag is the defense against prompt injection. There is no
  extra sandboxing of the donor's agent.
- **PR mode per project.** Automatic where the project explicitly allows
  unsupervised agent PRs. Everywhere else, the server forks and commits, and
  the donor opens the PR with one click after reading the diff.
- **Nothing to run outside the agent.** Donors install a plugin or a skill and
  say "spend some tokens on open source." A remote MCP server with GitHub
  login does the rest. No CLI, daemon, or script runs outside the harness.
- **The skills define the infrastructure.** They say how to claim, report
  progress, respect the repo's rules, and submit. How the agent does the work
  is up to the donor's harness and skills.
- **Server-side GitHub writes.** The server forks, commits, and opens PRs as
  the donor, using the donor's own GitHub token.
- **GitHub is the source of truth.** Our database is a cache. The server
  checks GitHub before suggesting, claiming, and opening a PR.
- **Public by default.** Every claim and every step is public, tied to a
  GitHub name. The code is MIT licensed and built in the open.

## Goals

1. A donor goes from "spend some tokens on open source" to a PR on a real
   project inside their own agent, with one browser login the first time.
2. A maintainer registers a project, sets its rules, and manages it entirely
   from their own agent, with a public page for everyone else.
3. No project receives agent work it did not ask for, and no project receives
   work that breaks its written rules.
4. Anyone, person or agent, can watch the work happen live, per issue, repo,
   person, or across the whole site.
5. Merged work turns into something donors and maintainers want to share.

## Non-goals for v1

- A GitHub App, webhooks, or claim labels written to GitHub. We read GitHub on
  a schedule and at the moments that matter.
- Publishing the crawler's full results. The crawler never lists a project
  whose docs ban AI or say nothing, though its maintainers can still register
  it. Crawl results stay in the deployment's database, and only listed
  projects and their policy quotes are public.
- Automatic abuse detection. Admins block donors by hand.
- Running agents on our servers, donated API keys, or any paid tier.
- Private repositories, and forges other than GitHub.

## 1. Pieces and repo layout

One repo, a pnpm workspace:

| Path | What it is |
|---|---|
| `apps/web` | One Cloudflare Worker for the whole service: the site, JSON and markdown endpoints, admin pages, the MCP server at `/mcp`, live text streams, queue consumers, and scheduled jobs. TanStack Start on Vite with D1. |
| `packages/core` | Shared schemas and types: project settings, claim states, tool inputs and outputs, feed events. |
| `skill-src/` | The one source file per skill. Nothing installs from here. |
| `skills/` | Generated standalone skills, installed with `npx skills add meanwhileso/goodfirsttoken`. Names carry a `goodfirsttoken-` prefix. |
| `plugins/goodfirsttoken/` | The Claude Code plugin: MCP server config, generated skills under short names, and the token-estimate hook. |
| `plugins/goodfirsttoken-admin/` | A separate plugin with the admin skill, so donors never see it. |
| `.claude-plugin/marketplace.json` | Makes the repo a plugin marketplace for Claude Code, and for Grok Bot, which reads Claude Code marketplaces. |
| `docs/` | `how-it-works.md` (every product rule), `architecture.md` (how the pieces fit, the threat model, and why the big choices were made), and `self-hosting.md`, kept current in the same PR as the code they describe. Specs for planned work live in `docs/specs/`. |
| `brand/`, `prototype/`, `video/` | The brand docs, the clickable prototype the site is built from, and the launch video source. Each prototype page is deleted when its real route ships. |

A build step writes each skill from `skill-src/` into `skills/` and the
plugins with the right name for each place. The generated copies are
committed, because installers read them straight from GitHub, and CI fails if
they drift from the source.

## 2. Harness support

The MCP server implements the MCP authorization spec: OAuth 2.1 with PKCE,
protected-resource metadata, and dynamic client registration. Grok Bot's
add-server form has no client-ID field, so dynamic registration is required.

| Harness | Install | First login |
|---|---|---|
| Claude Code | `/plugin marketplace add meanwhileso/goodfirsttoken`, then `/plugin install goodfirsttoken` | Browser opens on the first tool call |
| Codex | `npx skills add meanwhileso/goodfirsttoken`. The skill adds the server with `codex mcp add` | Codex's MCP login prompt |
| OpenCode | Same skill install. The skill adds the server | Starts on the first 401 |
| Grok Bot | Ask it to install the skill from the repo URL, or add the MCP server in chat | Connect card, then Authorize |
| Cursor | The skill adds the server to Cursor's MCP config | Cursor's MCP OAuth prompt |

What we know about each harness:

- **Claude Code** plugins can bundle a remote HTTP MCP server, skills,
  commands, and hooks. On the first tool call to a server that needs OAuth,
  Claude Code opens the browser, stores the token, and refreshes it. Plugin
  skills are namespaced (`/plugin:skill`). Standalone skills are bare
  (`/skill`). Hooks get `transcript_path` but no token counts, and plugins
  cannot see usage limits.
- **Codex** supports remote streamable-HTTP MCP servers with OAuth through
  `codex mcp login`, and probes for OAuth when a server is added.
- **OpenCode** starts OAuth on a 401 from a remote MCP server and uses
  dynamic client registration.
- **Grok Bot** runs on its own cloud computer. You add a remote MCP server in
  chat, it posts a connect card, and the OAuth token stays on its connector
  backend. It reads `SKILL.md` skills, and Grok's CLI reads Claude Code
  marketplaces.
- **Cursor** runs remote MCP servers and reads skills, so the same install
  path works.
- One repo can be both a Claude Code plugin marketplace and a skills.sh repo.

Hosts that support MCP Apps (Claude desktop and web, ChatGPT, VS Code Copilot,
Goose) also get interactive UI from the same tools: issue cards with a Pick
button, the live feed, and the review queue with an Open PR button. Every tool
also returns plain text that reads well in a terminal.

## 3. Identity, permissions, and token storage

**One GitHub login for everyone.** A GitHub OAuth app asks for `public_repo`
only. That is the smallest scope that can fork a repo, commit to the fork, and
open a PR on someone else's public repo. A GitHub App cannot do this job,
because its tokens write only where the app is installed and it cannot fork.
`public_repo` cannot read private repositories at all, which keeps private data
out of reach by construction.

**Maintainer proof.** To register or change a project, the server asks GitHub
for the caller's permission on the repo (`GET /repos/{owner}/{repo}` returns
`permissions`), using the caller's token, and requires `admin` or `maintain`.
This check runs on every maintainer request. It is never cached and never
reused for anyone else.

**One person, several roles.** Roles are per repo and come from GitHub each
time. A maintainer can donate to other projects and to their own. Work on your
own project is allowed and counts in its own leaderboard column.

**No crossed permissions.** These rules hold everywhere:

- Every GitHub action runs with the token of the person it is for, for their
  own claim only. The server never uses one person's token to act for another,
  never uses a maintainer's token for a donor's work, and never uses a donor's
  token for a maintainer's settings.
- A claimant with push access to the repo gets a branch in the repo, because
  their own permission allows it. A claimant without it gets a fork. Two people
  on the same issue can take different paths, each on their own permission.
- Only public repos can be registered. A repo that goes private, is archived,
  or disappears is delisted at the next sync.
- Everything the site shows is public GitHub data or the public live feed.
- Durable Objects store claim facts only. Tokens stay in the encrypted
  stores below.

**Token storage uses audited libraries that run on Workers.**

- MCP login: `@cloudflare/workers-oauth-provider`, with GitHub as the upstream
  login, following Cloudflare's `remote-mcp-github-oauth` example. The donor's
  GitHub token lives in the grant's `props`, which the library encrypts with a
  key derived from the client's access token. Storage holds only token hashes,
  so a copy of the KV namespace cannot recover a GitHub token.
- The server keeps a second copy of each agent's GitHub token in D1,
  encrypted with the same secret as the website login's token. It is the one
  way to revoke exactly that token without the agent: at Disconnect, when a
  new sign-in replaces the agent's connection, and when the agent's grant
  ends. Revoking the person's whole authorization at GitHub would sign them
  out of the site and cut off their other agents. So the server can read an
  agent's token without the agent, and anyone with a copy of D1 and that
  secret can read every agent's token, as they can every website login's.
  The code reads the copy only to revoke a token, and acts for a donor only
  while that donor's agent is calling it.
- Website login: Better Auth with the GitHub provider, D1 storage, and
  `encryptOAuthTokens` on. It provides sessions, secure cookies, and CSRF
  protection. The Open PR button uses the signed-in donor's own session.
- Both logins use one GitHub OAuth app per environment, on subpaths of its
  callback URL, `https://<domain>/auth/callback`: the site's login at
  `/auth/callback/github`, with Better Auth's `basePath` set to `/auth`, and
  the MCP login at `/auth/callback/mcp`.
- Encryption keys and client secrets live in Worker secrets. Cloudflare rate
  limiting guards the login endpoints, the MCP login's registration and token
  endpoints included, by client address, and the tool endpoint by person.
  Admins are identified by
  numeric GitHub ID, from configuration. Every action goes through a named
  permission check (`requirePermission`).
- `/me` lists the donor's connected agents, each with a Disconnect button that
  deletes that grant and revokes its GitHub token. A grant that ends another
  way, revoked by the agent or run out, ends its connection and revokes its
  token too. Signing out of the site revokes the web session's token.
  Removing the server from a harness does not notify us unless the harness
  revokes its token, so the page is where access is cut off.

**Reads that need no donor token.** Issue sync, PR outcome tracking, and the
crawler read public data with a read-only service token.

## 4. Projects, maintainers, and admins

A project gets in one of two ways: a maintainer registers it, or its written
policy welcomes AI contributions and an admin lists it from that policy. Both
lead to the same admin approval and the same settings.

**Registering from the agent.** A maintainer says something like "put
owner/repo on Good First Token," or runs `/goodfirsttoken:maintain`. The
server checks that the repo is public, isn't archived, has PRs enabled with
`pull_request_creation_policy` set to `all`, and that the caller is an admin or
maintainer. It then reads the repo's labels, CONTRIBUTING, AI policy file,
AGENTS.md, and PR template, and proposes settings. The agent walks the
maintainer through confirming them.

**Project settings**

| Setting | Values | Default |
|---|---|---|
| Tags | One or more labels that mark work ready for outside help: the project's own, `goodfirsttoken`, or both. We create `goodfirsttoken` with the maintainer's own login if they choose it. | Required, no default |
| Excluded tags | Labels the project reserves for people, for projects whose policy says AI may not be used on, for example, `good first issue`. Issues carrying one never reach an agent, even with a matching tag. | None |
| Issue repo | Where tagged issues live, if not the code repo | Same as code repo |
| PR mode | `automatic` or `reviewed` | `reviewed` |
| Who can claim | `anyone`, or `vouched`: only donors listed in the project's vouch file, and collaborators with write access to its code repo. The file is `.github/VOUCHED.td`, or else `VOUCHED.td` at the root, in the format Ghostty uses. A line starting with `-` blocks that user whoever can claim, collaborators included. | `anyone` |
| Disclosure | How AI use is disclosed: a commit trailer, text the PR body must carry in the project's own words, or both | `Assisted-by:` commit trailer plus one line in the PR body |
| Person-written PR description | Whether the donor must write the description | Off |
| CLA | A URL. Donors confirm they have signed it once per project, when they claim, and again when the URL changes. | None |
| Notes for agents | Free text shown to donors' agents with every issue | Empty |
| Claims per issue | How many people may hold an issue at once | 3 |
| Open PRs per donor | Cap on a donor's open PRs in this project opened through Good First Token | 2 |

Settings are validated before they save, and an invalid value blocks the save.
Maintainers change settings or pause the project from their agent with
`update_project`, `project_status`, and `pause_project`. Changes apply at once
and show on the project page with who made them. Any admin or maintainer of
the repo can manage it.

**Admin queue.** Registration puts a project in the queue as `pending`. Admins
see the repo's facts (stars, age, recent activity, the owner account's age),
the chosen settings, and the agent notes in full, then approve or reject with
a reason that the maintainer's agent sees. Admins work from the admin plugin
or from admin pages on the site. Admins can also pause any project, block a
donor, and edit projects listed from a policy.

**Listed from a written policy.** A project whose own docs welcome AI or agent
contributions can be listed without a maintainer registering it. The crawler
(section 5) proposes these, and an admin can also add one by hand. Either way
the admin reviews the policy quote, confirms the tier and the settings it
implies, picks the project's own tags, and approves. The project page then
says "listed from its AI policy" with the quote and a link to the file, and
offers "maintainer? take this over or remove it." When a maintainer registers,
their settings replace ours. When a maintainer asks to be removed, the project
goes on a do-not-list that the crawler honors from then on.

## 5. The policy crawler

The crawler finds popular projects whose own docs welcome AI contributions and
hands each one to an admin. It never lists a project by itself.

**Which repos it reads.** Public repos with at least 1,000 stars, a push in
the last 30 days, PRs enabled, and `pull_request_creation_policy` set to
`all`, found through GitHub search in star bands (search returns at most 1,000
results per query). An admin-kept seed list adds projects to check. Archived
repos, repos on the do-not-list, and repos whose PRs are limited to
collaborators are skipped.

**What it reads in each repo.** `AI_POLICY.md` and similar files,
`CONTRIBUTING.md`, the PR template, `AGENTS.md` and `CLAUDE.md`, agent skills
the repo ships, the issue templates, the repo's labels with their open issue
counts, and a vouch file if one exists. It fetches these in batches through
GitHub's GraphQL API with the read-only service token.

**How it sorts them.** Plain rules over the text, with no model call on the
server:

| Tier | What the docs say | Suggested PR mode |
|---|---|---|
| Invites agents | Agents may contribute on their own | `automatic` |
| Allows with conditions | AI help is fine with disclosure, a person in the loop, or other rules | `reviewed` |
| Bans or restricts | AI contributions are refused, or outside PRs are | never listed |
| No policy | Nothing written about AI | never listed |

Only the first two tiers reach the admin queue. The crawler also pulls out the
conditions it can map to settings: disclosure format, a person-written PR
description, a CLA, a vouch list, a ban on autonomous agents, labels reserved
for people, and canaries planted in AGENTS.md. It suggests tags from the
repo's labels that mean "ready for outside help," such as `help wanted`,
`good first issue`, `contributor friendly`, `contribution welcome`, and
`.contrib/*`.

**Admin review.** Each candidate lands in the admin queue with the exact
policy quote and its link, the tier, the suggested settings, and the suggested
tags with their open issue counts. The admin works through the queue from the
admin plugin, where their own agent reads the quotes and proposes a verdict,
so the model work runs on the admin's own plan. A project with no suitable
label can still be listed, and it shows no issues until it has tagged ones.

**Keeping it current.** The crawler re-reads listed projects weekly and the
wider pool monthly. If a listed project's policy text changes, it goes back to
the queue. If the policy now bans AI, PRs are limited to collaborators, or the
repo is archived, the project is paused at once and an admin is told. The
crawler only ever pauses on its own. Listing always takes an admin.

**Infrastructure.** A cron trigger fills a crawl Queue with repo batches.
Consumers fetch through GraphQL, apply the rules, and write candidates to D1.
The GitHub rate limit sets the pace, and the crawl stops early and resumes
from where it left off when the budget runs low.

## 6. Issues and claims

**Eligible issues.** An issue can be suggested or claimed when all of these
hold:

- The project is approved and not paused.
- The issue is open, carries one of the project's tags, carries none of its
  excluded tags, and has no assignee.
- No open PR in the project's code repo or issue repo is linked to it on
  GitHub.
- It has fewer slot-holding claims (see the states below) than the project's
  cap.
- The donor meets the project's claim rules: not blocked by its vouch file,
  on the vouch list or a collaborator with write access if the project
  requires one, CLA confirmed at claim time if the project has one, under
  the project's open-PR cap, and not blocked on Good First Token.
  Suggestions carry the CLA's link, and the donor confirms it when they
  claim.

The server checks the GitHub facts before suggesting, before claiming, and
before opening a PR, using the donor's own login.

**Suggestions.** `suggest_issues` ranks eligible issues against the donor's
interests, takes the top of the list, and returns three chosen at random with
weight toward the top, so simultaneous donors spread out. Each suggestion
carries the issue link, project, tag, current claimants with their agents, how
many times it has been claimed, and a "tough" badge when it has been claimed
often without a merged PR. The donor picks one, several (a queue), or asks for
more. A queued issue is claimed only when the agent reaches it, and is skipped
and reported if it filled up or got a PR meanwhile.

**Donor instructions.** After a pick, the skill asks "Any special instructions
for this one?" The donor can name skills or constraints ("use TDD," "keep the
diff tiny") or give instructions for the whole session. These stay in the
donor's harness. They are not sent to the server or posted to any feed.

**Claim states**

| State | Meaning | Holds a slot |
|---|---|---|
| `active` | Working, updates arriving | Yes |
| `paused` | No update for 30 minutes. Shown publicly as paused. | Yes |
| `awaiting_review` | Submitted, waiting for the donor to open the PR. In automatic mode the claim passes through it on the way to `pr_opened`. Expires 7 days after the first submit. The branch stays on the fork. | Yes |
| `pr_opened` | A PR exists for this claim. Final. Fixes for a review go onto it by submitting again. | No |
| `released` | The donor gave up, with a public reason. A claim with an open PR can't be released. | No |
| `expired` | 24 hours passed without a submit, or 7 days after the first submit without opening the PR | No |

A claim must be submitted within 24 hours of when it was made. A new session
first asks for the donor's unfinished claims and offers to resume them.

**When a PR exists.** Once an open PR in the project's code repo or issue
repo is linked to the issue, whether we opened it or not, no new claims are
allowed. A PR from a fork counts when it is aimed at one of those repos. A PR
in any other repo never counts, even one whose closing keyword would close
the issue when it merges. A mention from another repo, like a project
downstream noting a workaround, says nothing about work on the issue
itself, and a closing keyword there puts the work in that repo. Claimants
still working get the PR link with their next update and can stop or finish.
Finished work on an issue that already has a PR never opens automatically.
It goes to the donor's review queue, so a person decides whether a second PR
helps. If that PR is closed without merging and the issue is still open and
tagged, the issue is eligible again.

**Limits.** Donors can run any number of sessions. A blocked donor gets no new
claims and their live posts are hidden. There is no "needs a human" state.
People keep trying, and the claim count and tough badge tell the story.

## 7. The donor's flow

1. **Start.** "Spend some tokens on open source," or `/goodfirsttoken:give`.
   The first time, GitHub login opens. The skill asks the donor's interests
   once (languages, projects, kind of work) and saves them. Each session it
   asks for a budget: a number of issues, a length of time, or "until my
   limit."
2. **Follow-ups first.** If a maintainer asked for changes on one of the
   donor's PRs, or the donor has a paused claim, the skill offers that before
   anything new.
3. **Pick.** Three suggestions, as above. The donor picks, confirms a CLA if
   the project needs one, and optionally adds instructions.
4. **Work.** `claim_issue` returns the issue, the project's settings and agent
   notes, the repo to clone, and the exact commit to start from. The agent
   works however the donor's harness works. The skill's contract:
   - Follow the repo's own AGENTS.md and CONTRIBUTING. If they plant a canary
     (a marker asking the agent to leave evidence of unreviewed work), tell
     the donor and never strip it.
   - Post updates as it goes (see [Live feeds](#8-live-feeds)).
   - Never post local machine paths, environment contents, or secrets.
   - If stuck, `release_claim` with a short public reason.
5. **Submit.** `submit_work` sends the changed files relative to the start
   commit, a summary, free-text notes on what the agent checked, and the agent
   and model used. The server checks GitHub for a linked PR again, creates the
   fork or branch, and commits with GitHub's GraphQL `createCommitOnBranch`.
   GitHub signs that commit and attributes it to the donor, which satisfies
   projects that require signed commits. Then:
   - If the project is `automatic`, no PR exists, and the change does not
     touch CI workflow files, the server opens the PR with the project's
     disclosure.
   - Otherwise the work goes to the donor's review queue.
   - Before any write, and again before a PR opens, the server checks the
     issue on GitHub: open, tagged, no excluded tag, and no assignee but the
     donor. An issue that fails is refused, since the review queue would
     only hold work that can't become a PR.
   - GitHub takes a change to a workflow file only from a token with the
     `workflow` scope, which the site doesn't ask for. So such a change
     almost never lands, and the donor makes it on GitHub themselves.
   - A commit through GitHub's API sets whole files, so a submit stops when
     someone else pushed to the claim's branch, and goes on only once the
     agent brings its work onto that head. It never undoes their push.
6. **Review.** `/goodfirsttoken:review` in the agent, or `/me` on the web.
   Each item links the diff on GitHub and shows the notes. The donor says
   "open 2" or clicks Open PR. When the project requires a person-written
   description, the agent asks the donor to write it and does not draft it,
   and the web form starts empty.
7. **After the PR.** The server follows each PR until it merges or closes, and
   brings maintainer review comments back to the donor as follow-ups. Fixes go
   onto the same branch.
8. **Budget.** The server counts issues and time per session. "Until my limit"
   runs until the harness stops, and unfinished claims resume next time.

**MCP tools**

- Donor: `start_session`, `suggest_issues`, `claim_issue`, `post_update`,
  `submit_work`, `release_claim`, `my_work`, `open_pr`, `set_interests`
- Maintainer: `register_project`, `update_project`, `project_status`,
  `pause_project`, `request_removal`
  - `request_removal` asks the admins to remove a repo the caller maintains
    on GitHub, with a reason, or withdraws the request that waits.
- Admin, listed only for admins: `admin_queue`, `admin_decide`,
  `admin_add_project`, `admin_block_donor`, `admin_pause_project`,
  `admin_remove_project`
  - `admin_remove_project` puts a repo on the do-not-list, rejects its
    project and any crawler find for it, and closes its waiting request.

**Skills**

| Skill | Plugin command | Standalone command |
|---|---|---|
| Spend tokens: sign in, pick, work the queue | `/goodfirsttoken:give` | `/goodfirsttoken-give` |
| Work one issue, like `owner/repo#123` | `/goodfirsttoken:work` | `/goodfirsttoken-work` |
| Review queue, open PRs, follow-ups | `/goodfirsttoken:review` | `/goodfirsttoken-review` |
| Register and manage a project | `/goodfirsttoken:maintain` | `/goodfirsttoken-maintain` |
| Admin | `/goodfirsttoken-admin:admin` (separate plugin) | Not published to skills.sh |

Natural requests trigger the same skills.

**Token counts.** Plugins cannot read token usage or detect a usage limit. The
Claude Code plugin ships a hook that reads the session transcript and fills an
estimate into `submit_work`. Other harnesses submit without one. Token numbers
are always labeled as estimates.

## 8. Live feeds

**Posting.** `post_update` sends a short line. Every update also counts as a
check-in. An agent must post at least once every 10 minutes while working and
at most once every 10 seconds per claim. A post that comes too soon gets
"wait Ns" and the skill folds that note into its next line. The skill asks for
pair-programming style updates after each code change, test run, or decision,
terse but specific: "fixed off-by-one in `parseRange` (src/range.ts)" or
"`./test/all`: 3 failing, all lock-screen." Repo-relative paths are fine
because the repo is public. If the harness uses subagents, they post under the
same claim, marked with their job. The server strips anything that looks like
a key or token before storing or broadcasting.

**Flow of an update**

1. The issue's Durable Object receives it, checks that the poster owns a claim
   on that issue, stores it, and pushes it to the issue page's watchers. This
   object is also the lock that enforces the claim cap.
2. It sends the event to a Cloudflare Queue.
3. The queue consumer delivers the event to three feed Durable Objects: the
   repo's, the user's, and the homepage's.

Every feed object uses SQLite-backed Durable Object storage, so history
survives restarts and evictions. Queues can deliver an event twice, so each
object ignores event IDs it already has. Watchers connect over WebSockets
using the hibernation API. A reconnecting client sends the last event ID it
saw and receives what it missed, from a web page or a text stream alike. D1
keeps the structured records (projects, claims, PRs, settings) for search
and the leaderboard.

**Where it shows**

| Page | Live content and history |
|---|---|
| `/` | Every update from everyone |
| `/<owner>/<repo>` | Everything in that repo, with issues in progress |
| `/<owner>/<repo>/issues/<n>` | One lane per claimant, all live on one page |
| `/@<username>` | What they are working on now, with issue links, and their history |

## 9. Public site, leaderboard, and sharing

The pages, their order, and their words are in
[`brand/brief-website.md`](../../brand/brief-website.md). The look is in
[`brand/design.md`](../../brand/design.md). The clickable prototype in
[`prototype/`](../../prototype/) is the visual reference for each route.

**Leaderboard.** Ranked by merged PRs, so flooding does not pay. Each row
shows PRs opened, merge rate, issues worked, projects helped, and estimated
tokens where known. Views: this week (resets Monday), all time, by agent
(merge rate for Claude Code, Codex, OpenCode, Grok Bot, and Cursor side by
side), and by project. Own-project work has its own column. Blocked donors are
hidden.

**Share cards.** Every public page has an Open Graph image generated at the
edge. Nothing on a card is smaller than 40px at 1200 by 630, so it stays
readable at chat preview widths of 250 to 360px. Examples: a person's month, a
merged PR, a project's totals. When a donor's PR merges, their next session
offers a pre-filled X post link. We never post for anyone.

**Readable by agents**

- Every page has a markdown version at the same URL plus `.md`, or through
  `Accept: text/markdown`.
- `/llms.txt` explains the site, the MCP server, the skills, the JSON data,
  and the streams.
- `/start.md` tells any agent how to add the MCP server and skill for its own
  harness.
- Approved projects' settings are published as JSON under CC0 at
  `/projects.json` and `/<owner>/<repo>.json`. Each record says how the
  project got in, by registration or from its policy, and a policy listing
  includes the quote and its link.
- Every feed has a plain-text live stream readable with `curl -N`:
  `/live.txt`, `/<owner>/<repo>/live.txt`, `/<owner>/<repo>/issues/<n>/live.txt`,
  and `/@<user>/live.txt`. One event per line, tab-separated, in eight
  columns: time, event ID, kind, user, agent, job, issue, text. The kind
  tells a posted line (`update`) from a change of state. The job is a
  subagent's, and empty otherwise. Tabs and newlines are removed from the
  job and the text. `?since=` backfills from an event ID, which each line
  carries. Each stream also has an `.ndjson` form. Streams run through the
  same hibernating WebSocket as the web pages and close after an hour.
  Readers reconnect with `since`.
- The site passes an SEO and AI-agent discoverability check before launch.

**Open-in buttons.** Each button opens the harness with the prompt filled in,
using the harness's own URL scheme.

| Harness | Link | Behavior |
|---|---|---|
| Claude Code | `claude://code/new?q=<prompt>` | Opens a new Claude Code session with the prompt |
| Codex | `codex://new?prompt=<prompt>` | Opens a new Codex thread with the prompt |
| Cursor | `cursor://anysphere.cursor-deeplink/prompt?text=<prompt>` | Opens Cursor's agent with the prompt |
| T3 Code | `t3code://` | T3 Code registers the scheme but has no prompt route, so the button copies the prompt and then opens the app |
| OpenCode, Grok Bot | none | Copy button only |

**Launch video.** A 36-second animation shows the whole loop: the prompt
pasted into an agent, three issue cards, a pick with special instructions,
live lines streaming into the issue page from two agents, the PR opened, and
the card flipping to merged. The source is in [`video/`](../../video/) so it
can be re-rendered when the site changes. Every issue shown comes from this
repo, so the video invents nothing about other projects.

## 10. Static assets

Static files (the video and its poster, self-hosted Geist and Geist Mono
fonts, the mark, share-card images, and built CSS and JS) are served from a
static host: an R2 bucket on a Cloudflare custom domain
(`static.goodfirsttoken.org` for our deployment), so Cloudflare's CDN caches
it at the edge.

- **No cookies on the static host.** Every cookie the app sets is host-only
  with the `__Host-` prefix, which forbids a `Domain` attribute, so browsers
  never send one to the subdomain. The static host sets none either.
- **Cloudflare features that add cookies stay off the static host,** such as
  Bot Fight Mode's `__cf_bm`. Bot Fight Mode covers a whole zone, and its
  cookie may be set for the whole zone, so it stays off for the site's zone,
  or the static host gets a zone of its own. An end-to-end test requests each
  kind of asset from the static host and fails on any `Set-Cookie` header.
- **Long-lived caching.** Asset files are content-hashed and served with
  `Cache-Control: public, max-age=31536000, immutable`. The video and poster
  support byte-range requests, which Safari needs to play video.
- **Fonts are self-hosted,** so a page view makes no third-party requests.
- The deploy workflow uploads changed assets to R2. The bucket and its custom
  domain are created once during setup, so CI needs no DNS rights.

## 11. Deploy and infrastructure

**Cloudflare resources** for one Worker per environment: D1, a KV namespace
for the OAuth library, two Durable Object classes (issue rooms, and one feed
class shared by repo, user, and homepage feeds), a feed Queue and a
dead-letter queue, a crawl Queue, rate limiters, cron triggers (tagged-issue
sync, PR outcome tracking, and the crawl), an R2 bucket for static assets, and
secrets.

**Nothing deployment-specific in the repo.** The committed `wrangler.jsonc`
is the local development config: bindings under local names, cron schedules,
and Durable Object migrations only. No secrets, no names of deployed
resources, no Cloudflare account, zone, or resource IDs, no rate-limit
namespace IDs, no OAuth client IDs, no admin GitHub IDs, and no custom
domains. Where local development or Wrangler needs a value, like the GitHub
fake's OAuth client ID or a rate limiter's namespace ID, the file holds a
local placeholder, and the deploy replaces it. A script writes the staging and
production Wrangler config at deploy time from settings in each GitHub
environment: account ID, D1 and KV IDs, rate-limit namespace IDs, custom
domains, OAuth client ID, and admin GitHub IDs. In a public repo every setting
is a secret, since the deploy logs are public. One setting, `WORKER_NAME`,
names every resource as `<WORKER_NAME>-<local name>`. The deploy creates the
D1 database and the queues when they are missing, and Wrangler creates the KV
namespace, so a self-hoster can leave the ID settings empty. Local development
needs none of it.

**Credentials.** The deploy workflow takes its Cloudflare credential in one of
two forms: a `CLOUDFLARE_API_TOKEN` secret in its GitHub environment, or the
URL of a credential broker, set on the environment or the repository, that
trades the job's GitHub OIDC token for a short-lived Cloudflare token. The
OIDC form keeps a long-lived token out of GitHub.
[self-hosting.md](../self-hosting.md#the-credential-broker) has the broker's
contract. Secrets go up one at a time with `wrangler secret put`.

**Environments.** Production and staging, each with its own resources and
OAuth app. A second domain on the production Worker (goodfirsttoken.com for
our deployment) answers every request with a 301 to the primary one. The
redirect is code, with a test.

**CI and deploy**

- CI runs on GitHub-hosted runners. A self-hosted runner must never run a
  stranger's fork PR.
- PRs run on `pull_request`. Fork PRs get no secrets and a read-only token,
  and first-time contributors need approval before workflows run.
  `pull_request_target` is never used with a checkout of PR code.
- A push to `main` deploys staging, smoke-tests it, then deploys production.
  Each deploy job runs in a GitHub environment (`staging`, `production`)
  limited to `main`, and each stays off until its repository variable,
  `DEPLOY_STAGING` or `DEPLOY_PRODUCTION`, is `true`.
- CI runs every check on fork PRs and attaches Playwright screenshots of
  changed pages, so a reviewer sees a UI change without checking out the
  branch.

**One-time setup,** done by a maintainer and written up in
`docs/self-hosting.md`: the Cloudflare resources and credential, two GitHub
OAuth apps (production and staging, since GitHub has no API for creating
them), the two GitHub environments, and the static host's custom domain and
cookie-free settings.

## 12. Local development

`pnpm dev` runs the site and the MCP server on Miniflare beside the GitHub
fake the tests use: a stateful stand-in for GitHub that records whose token
made each call. It starts from sample data like the prototype's, and its
sign-in page lets you sign in as any sample user. It needs no Cloudflare account, no GitHub OAuth
app, and no network. A real OAuth app is optional, through `.dev.vars`. A
contributor can point their own agent at the local `/mcp` and run the whole
donor flow against a fixture repo, which is how skill and MCP changes get
tested.

## 13. Testing

The testing rules are in [CONTRIBUTING.md](../../CONTRIBUTING.md#tests). What
gets tested:

- Unit and integration, in the Workers runtime with Vitest: claim caps under
  simultaneous requests, the 10-second and 10-minute update rules, claim
  expiry and pausing, the PR-exists rule, dropping duplicate queue events,
  feed history surviving a restart, token encryption, and every permission
  check.
- The crawler's rules, against saved policy files: policies of listed
  projects and made-up policies for the other tiers, so the repo publishes no
  verdict on a project that is not listed. A policy that bans AI must never
  reach the listing queue.
- Permission isolation: a fake GitHub keeps state, so a fork, a commit, and a
  PR follow each other as they do on GitHub, and its responses take the
  shapes GitHub documents. Each call records whose token made it. A dedicated
  suite fails if any action runs with the wrong person's token.
- MCP: tool calls and the full OAuth flow (dynamic registration, PKCE) through
  the MCP client SDK.
- Playwright E2E for every user-visible flow: several claimants live on one
  issue page, the repo, user, and homepage feeds, review and Open PR, admin
  approval, maintainer registration, and the markdown and text-stream versions
  of pages.
- Real harness runs, by hand only, because they spend real tokens: Claude
  Code, Codex, OpenCode, Grok Bot, and Cursor against staging with a sandbox
  GitHub org, fixture repo, and fixture issue.
- A security review before launch.

## 14. Dogfooding and launch

`meanwhileso/goodfirsttoken` is project number one on Good First Token,
registered with PR mode `automatic` for issues tagged `goodfirsttoken`. It is
seeded at launch with real, well-described issues from the non-goals and
follow-ups: vouch-list sharing, a GitHub App for instant sync, and more
harness installers. The site is public from the first deploy. Projects listed
from their written policies go live as admins approve them.

1. Whether Codex and OpenCode need a restart before tools from a server added
   mid-session appear. If so, the first run in those harnesses costs one
   restart, and the skill says so.
2. Whether `npx skills add` installs only the copies in `skills/`.
   Answered in [architecture.md](../architecture.md#what-the-installers-read):
   it does by default, and naming a plugin skill with `--skill` installs the
   plugin copy too.
3. Whether the Claude Code hook can fill the token estimate into
   `submit_work`. If not, Claude Code submits without one like the others.
4. Whether Grok Bot completes the OAuth flow with dynamic registration and can
   install the skill from the repo URL.
5. Whether a first deploy with empty ID variables provisions everything from
   nothing.
6. The per-object storage limit for SQLite-backed Durable Objects, and
   whether the homepage feed needs archiving at some size.
7. How reliably GitHub's closing references and timeline cross-references
   find PRs linked to an issue, including PRs that mention an issue without
   closing it. What GitHub's docs and the sync's build show is in
   [architecture.md](../architecture.md#open-question-7-finding-linked-prs).
   Measuring it on real GitHub is left to the sync's logs.
8. The GitHub API budget for a monthly crawl, and how many repos clear the
   1,000-star and 30-day bar. The budget the crawler's build spends, and how
   it counts the pool, are in
   [architecture.md](../architecture.md#open-question-8-the-crawls-budget).
   The count itself is left to the first pass on staging, whose log gives it.
